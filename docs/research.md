## 2. 환경 측정 결과

### 2.1 디스플레이 구성

```
id=1  bounds=    0,   0   2056x1329 (pt)   pixels=2056x1329   scale=1.00x   (내장 Liquid Retina XDR)
id=2  bounds=-3840,-467   3840x2160 (pt)   pixels=3840x2160   scale=1.00x   (외장 4K)
id=3  bounds= 2056,-317   2560x1440 (pt)   pixels=2560x1440   scale=1.00x   (외장 QHD)
```

여기서 설계에 직결되는 두 가지 사실이 나왔다.

**(1) Retina 2배 스케일 문제가 이 환경에는 없다.**
내장 디스플레이가 스케일 모드로 동작 중이라 `CGDisplayPixelsWide / bounds.width == 1.00`이다.
즉 **논리 좌표(point)와 실제 픽셀이 1:1**이고, 클릭 좌표를 그대로 캡처 좌표로 쓸 수 있다.
일반적인 macOS 화면 자동화의 최대 함정이 이 환경에서는 비켜간 셈이다.

> 다만 이 값은 사용자가 디스플레이 해상도 설정을 바꾸면 달라진다.
> 따라서 **하드코딩하지 말고 실행 시점에 `CGDisplayPixelsWide / CGDisplayBounds().size.width`로
> 스케일 팩터를 측정**하고, 1.0이 아니면 좌표를 환산한다. (→ `display.py`)

**(2) 전역 좌표계에 음수가 존재한다.**
왼쪽 4K 모니터가 `x = -3840`에서 시작한다. 데스크톱 전체 경계는
`left=-3840, top=-467, width=8456, height=2160`이다.
**좌표를 다루는 모든 코드가 음수를 전제로 작성되어야 한다.** 이것이 아래 2.3의 결론을 낳았다.

### 2.2 캡처 성능 (mss 10.2.0)

```
첫 grab (콜드 스타트)   : 79 ms
이후 grab 평균 (5회)    : 12 ms      ← 2056x1329 전체 화면 기준
요청 pt 대비 실제 px 비율: 1.00x
```

12ms면 사용자가 지정할 캡처 간격(최소 단위가 초)에 비해 **3자릿수 여유**가 있다.
캡처 속도는 이 프로젝트의 병목이 아니다. 성능 최적화는 불필요하다 (YAGNI).

### 2.3 클릭 제어: pyautogui vs Quartz — **pyautogui 탈락**

가장 중요한 조사 결과다. 두 후보를 같은 환경에서 비교했다.

```
pyautogui.size()  ->  Size(width=2056, height=1329)      ← 주 디스플레이만 인식
```

pyautogui는 데스크톱 전체(8456×2160)가 아니라 **주 디스플레이 크기만 보고**한다.
왼쪽 4K 모니터의 좌표(x = -3840 ~ 0)를 주소 지정할 수 없다는 뜻이다.
전자책 뷰어를 외장 모니터에 띄우고 캡처하는 것이 이 도구의 가장 자연스러운 사용 시나리오인데,
pyautogui를 쓰면 **주 디스플레이에 뷰어를 띄워야만 동작하는 제약**이 생긴다.

반면 Quartz `CGEventCreateMouseEvent`는 음수 전역 좌표를 정확히 처리한다 (이벤트 생성 후 좌표 회독):

```
requested (-2000, 500) -> event location (-2000, 500)   OK
requested (  100, 100) -> event location (  100, 100)   OK
requested ( 3000, 800) -> event location ( 3000, 800)   OK
CGEventPost available: True
```

**결론: pyautogui를 스택에서 제외하고 Quartz `CGEventPost`로 직접 클릭한다.**
부수 효과로 의존성이 크게 줄었다 — pyautogui는 pyscreeze, pygetwindow, pymsgbox, pytweening,
pyrect, mouseinfo, pyperclip 등 7개 패키지를 끌고 들어오는데 이 중 어느 것도 필요하지 않다.
Quartz(`pyobjc-framework-quartz`)는 디스플레이 열거를 위해 **어차피 필요한 의존성**이라 순증가가 0이다.

### 2.4 OCR 실현성 (tesseract 5.5.2 + pytesseract)

진행률 판독이 R6의 핵심이자 이 프로젝트 최대 리스크다. 합성 라벨로 정확도와 속도를 측정했다.

| 폰트 크기 | 기대값 | 인식 결과 | 소요 |
|---|---|---|---|
| 14px | `47%` | `47%` | 90ms |
| 14px | `100%` | `100%` | 60ms |
| 22px | `47%` | `47%` | 70ms |
| 22px | `100%` | `100%` | 60ms |

적용한 설정: **3배 LANCZOS 업스케일 + `--psm 7`(단일 텍스트 라인) + 숫자 화이트리스트**

```
--psm 7 -c tessedit_char_whitelist=0123456789.%/
```

작은 UI 폰트(14px)도 3배 업스케일하면 100% 맞혔다. 호출당 60–90ms로 캡처 간격에 비해 무시할 수준이다.

> **단, 이것은 흰 배경·검은 글자의 합성 이미지 기준이다.**
> 실제 뷰어는 안티에일리어싱, 반투명 오버레이, 다크 모드, 저대비 회색 글자일 수 있다.
> 그래서 OCR을 **단독 종료 조건으로 쓰지 않는다** (→ 3.2 이중 안전장치).

### 2.5 PDF 병합 (img2pdf 0.6.3)

```
3 페이지 병합        : 11 ms
JPG 합계             : 987,900 bytes
생성된 PDF           : 990,337 bytes      ← 차이 2.4KB (PDF 구조 오버헤드뿐)
페이지 MediaBox      : 493.44 x 318.96 pt = 6.85" x 4.43"
내장 이미지 필터     : /DCTDecode, 2056x1329
```

`/DCTDecode`는 **JPEG 원본이 재인코딩 없이 그대로 삽입**되었다는 뜻이다.
PDF 크기가 JPG 합계와 사실상 같은 것이 그 증거다. 화질 손실이 0이고 속도도 페이지당 4ms 미만이다.

대안이었던 `Pillow.save(save_all=True)`와 `reportlab`은 둘 다 이미지를 다시 인코딩하거나
래핑 과정에서 품질·용량 제어가 불투명해 탈락시켰다.

## 3. 핵심 설계 판단

### 3.1 "300dpi"의 의미 — 반드시 짚고 넘어가야 할 지점

화면 캡처는 물리적으로 화면의 픽셀 수만큼만 존재한다. 이 머신의 내장 디스플레이는
2056×1329px이고, **없는 디테일을 300dpi로 만들어낼 수는 없다.**
"300dpi"는 두 가지로 해석 가능하고, 결과가 크게 다르다.

| 방식 | 처리 | 결과 | 평가 |
|---|---|---|---|
| **A. DPI 메타데이터만 300으로 기록** | 픽셀은 원본 그대로, JPEG 헤더에 300dpi 태그 | 2056×1329px → PDF 페이지 6.85"×4.43". 인쇄 시 **실제 300dpi 밀도** | **채택** |
| B. A4 300dpi(2480×3508px)로 업스케일 | LANCZOS 확대 | 페이지는 A4지만 **디테일은 늘지 않고** 파일만 4~6배 커짐 | 기각 |

**A를 채택한다.** 측정에서 확인했듯 img2pdf가 JPEG의 DPI 메타데이터를 읽어 페이지 크기를
자동 계산한다(6.85"×4.43"). 페이지의 물리적 크기는 작지만 화소 밀도는 진짜 300dpi이고,
어떤 PDF 뷰어에서도 원본 화질 그대로 확대해서 볼 수 있다.

> **실용 팁**: 더 많은 실제 픽셀을 원하면 업스케일이 아니라 **뷰어를 4K 외장 모니터(3840×2160)에
> 띄우고 캡처**하면 된다. 같은 지면에서 픽셀 수가 약 3배가 된다. 2.3에서 pyautogui를 버리고
> Quartz를 택한 덕분에 이 시나리오가 가능하다.

옵션으로 `--page-size a4`를 제공해, 픽셀은 건드리지 않고 **PDF 페이지 박스만 A4에 맞춰 배치**하는
모드를 둔다(img2pdf `layout_fun`). 이건 업스케일이 아니라 배치 변경이라 화질 손실이 없다.

### 3.2 종료 판정 — OCR 단독 금지, 이중 안전장치

R6은 "진행률 100%면 중단"이지만 OCR은 본질적으로 실패할 수 있다(2.4 단서 참조).
OCR이 `100`을 놓치면 **루프가 영원히 클릭하며 같은 화면을 수천 장 저장**한다. 이건 반드시 막아야 한다.

세 겹으로 방어한다.

1. **주 판정 — OCR**: 사용자가 지정한 진행률 영역을 매 회차 작게 grab(12ms) → 3배 업스케일 →
   화이트리스트 OCR → `100` 이상이면 정상 종료.
2. **보조 판정 — 화면 변화 감지**: 직전 캡처와 현재 캡처의 해시/평균 절대차를 비교해
   **N회 연속(기본 3회) 동일**하면 "더 넘길 페이지가 없다"로 보고 종료.
   OCR이 실패해도 여기서 반드시 걸린다.
3. **하드 상한**: `--max-pages`(기본 2000) 도달 시 무조건 중단.

여기에 **`ESC` 전역 중단 키**를 더한다. 자동 클릭 루프가 도는 중에는 사용자가 마우스를 쓸 수 없으므로,
키보드로 즉시 멈출 수단이 없으면 위험하다. pynput 키보드 리스너로 상시 감시한다. **이건 선택이 아니라 필수다.**

### 3.3 좌표 수집 방식

UI는 "터미널 + 화면 클릭 수집"으로 확정되었다. pynput의 전역 마우스 리스너로
사용자의 실제 클릭을 가로채 좌표를 얻는다. 총 5점을 순서대로 수집한다.

```
1) 캡처 영역 좌상단      (전체 화면 모드면 생략)
2) 캡처 영역 우하단      (전체 화면 모드면 생략)
3) 다음 페이지 클릭 지점
4) 진행률 표시 영역 좌상단
5) 진행률 표시 영역 우하단
```

수집 직후 **각 영역을 한 장씩 캡처해 미리보기 파일로 저장**하고 사용자에게 확인받는다.
좌표를 잘못 잡은 채로 300장을 캡처하는 사고를 막는 가장 싼 방법이다.

수집한 설정은 `result/<제목>.session.json`에 저장해 **중단 후 재개**가 가능하게 한다.

## 4. 최종 스택

| 화면 캡처 | **mss** | 10.2.0 | 12ms/frame, 멀티모니터 음수 좌표 지원, 순수 캡처에만 집중 | pyautogui.screenshot (느림, 주 디스플레이 한정) |

| 클릭 좌표 수집 | **pynput** | 1.8.2 | 전역 마우스/키보드 리스너. ESC 중단키도 여기서 처리 | — (대안 없음) |

| 이미지 처리 | **Pillow** | 12.3.0 | JPEG 인코딩, DPI 메타데이터, OCR 전처리 업스케일 | — |
| PDF 생성 | **img2pdf** | 0.6.3 | **JPEG 무손실 패스스루(/DCTDecode)**, 페이지당 4ms | Pillow save_all, reportlab (재인코딩) |
| 패키지 관리 | **uv** | 설치됨 | 설치 476ms. 프로젝트 venv 격리 | pip, poetry(미설치) |
| CLI | **argparse** (표준) | — | 의존성 0. 대화형 프롬프트는 `input()`으로 충분 | typer, click, rich (이 규모엔 불필요) |

```toml
dependencies = [
  "mss>=10.2",
  "pynput>=1.8",
  "pyobjc-framework-Quartz>=12.2",
  "Pillow>=12.3",
  "pytesseract>=0.3.13",
  "img2pdf>=0.6.3",
]
```

시스템 의존성: `tesseract` (Homebrew, 설치 완료)

## 5. macOS 고유 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **화면 기록 권한** (TCC) | 없으면 캡처가 **검은 화면 또는 배경화면만** 반환 — 조용히 실패한다 | 미리보기 캡처가 완전한 단색이면 경고를 출력한다 (구현 노트: 아래 참고, 종료하지 않음) |
| **손쉬운 사용 권한** | 없으면 `CGEventPost` 클릭과 pynput 리스너가 **무반응** | 리스너 시작 후 타임아웃 검사로 조기 감지 |
| 권한은 **터미널/IDE 앱**에 부여됨 | python 실행 파일이 아니라 부모 앱 기준. VS Code에서 실행하면 VS Code에 권한 필요 | README에 명시 |
| macOS 15+ 권한 주기적 재확인 | 장기 사용 시 갑자기 캡처 실패 | 매 실행 시 권한 검사(위와 동일 경로) |
| 디스플레이 해상도 변경 시 스케일 변동 | 좌표 어긋남 | 런타임 스케일 측정 (2.1), 세션 재개 시 재검증 |
| 자동 클릭 중 사용자 마우스 조작 불가 | 루프 중단 수단 없음 | **ESC 전역 중단키 필수** (3.2) |

> **구현 노트 (최종 리뷰 반영)**: 위 표는 원래 "전 픽셀 동일 여부 검사, 실패 시 종료"를
> 대응책으로 제시했지만, 실제 구현(`cli.py`의 `save_previews`)은 **종료하지 않고 경고만
> 출력**한다. 이유는, 진행률 판독 영역처럼 실제로 완전한 단색(흰 배경 등)인 것이 정상인
> 화면이 있을 수 있고, 대상 앱의 특정 페이지가 우연히 단색 이미지(표지, 여백 페이지 등)일
> 수도 있기 때문이다. 이런 경우까지 하드 종료시키면 정상적인 캡처를 막는 오탐이 된다.
> 대신 단색 미리보기를 감지하면 "권한이 아직 적용되지 않았을 수 있다"는 한국어 경고를
> 띄우고, 기존과 동일하게 사용자가 미리보기 파일을 직접 눈으로 확인해 계속할지 판단하게
> 한다.

### 6.2 진행률 OCR — **실제 UI에서 검증 완료**

5절의 최대 리스크였던 항목이다. 실제 화면에서 진행률 표시를 픽셀 단위로 찾아냈다.

```
진행률 텍스트 bbox : x 73 -> 92,  y 1960 -> 1970
글리프 크기        : 11 px 높이 x 20 px 너비        ← 매우 작음
텍스트 색          : RGB(68, 68, 68)  진회색
배경 색            : RGB(255, 255, 255) 흰색        ← 대비 충분
표기 형식          : "0%"  (정수 + % 기호, 소수점 없음)
위치               : 창 좌측 최하단, 책 페이지 영역 바깥
```

11px 글리프는 OCR에 불리한 크기라 우려했으나, 여유 있게 크롭(120×34)한 뒤 업스케일해
tesseract를 돌린 결과 **모든 배율에서 정확히 인식**했다.

| 업스케일 | `--psm 7` | `--psm 8` |
|---|---|---|
| ×2 | `0%` | `0%` |
| ×3 | `0%` | `0%` |
| ×4 | `0%` | `0%` |
| ×6 | `0%` | `0%` |
| ×8 | `0%` | `0%` |

**결론**: 대비가 68 대 255로 충분해서 작은 글리프임에도 안정적이다.
3.2의 OCR 주 판정 설계를 그대로 유지한다. 기본 업스케일은 **×4**로 정한다
(×2도 통과했으나 여유를 두고, ×6 이상은 이득 없이 느려지기만 한다).
`--psm 7`을 기본으로, 실패 시 `--psm 8`로 1회 재시도한다.

> 이진화(Otsu)·대비 보정 전처리는 **불필요한 것으로 판명되어 설계에서 제외**한다. (YAGNI)

**추가 (2026-09-16)**: 뷰어에 따라 진행률을 `1/762` 처럼 **쪽/전체**로 표시하기도 한다.
합성 라벨 검증 결과 tesseract가 `1/762`, `123/762`, `762/762`, `1 / 762` 를 모두 정확히
읽었다(`/` 는 이미 화이트리스트에 있다). 쪽/전체는 백분율로 환산해 처리하므로 종료 판정
로직은 그대로다. 한 영역에 `%` 와 분수가 함께 잡히면 **`%` 를 우선**한다 — `%` 로 표시하는
뷰어에서 영역에 쪽 번호가 섞여도 6.2에서 확인한 안전성을 유지하기 위함이다.
그 대가로 `%` 가 전혀 없는 영역에서는 `p 100 / 350` 같은 쪽 번호가 진행률로 해석될 수 있다.
쪽/전체 표기를 지원하려면 피할 수 없는 맞바꿈이다.

**중요**: 진행률 표시가 **책 페이지 영역 바깥**(좌측 최하단)에 있다.
3.3에서 캡처 영역과 OCR 영역을 별도로 받도록 설계한 것이 실제로 필요했음이 확인되었다.

### 6.3 캡처 영역 — 전체 화면 캡처는 70%가 낭비

뷰어 창은 3206×2055지만, 실제 책 페이지는 창의 왼쪽 일부만 차지한다.

```
책 페이지 bbox : x 73 -> 1177,  y 60 -> 1835
페이지 크기    : 1105 x 1776 px  (종횡비 0.622)  = 1.96 MP
창 전체        : 3206 x 2055 px                  = 6.59 MP
페이지 비중    : 30%      ->  전체 창 캡처 시 매 장 70%가 흰 여백
```

**전체 화면 모드로 캡처하면 파일 크기가 3.3배가 되고 PDF도 그만큼 커진다.**
영역 지정 모드가 선택 기능이 아니라 **이 사용 사례의 기본값**이어야 한다.
CLI 기본 동작을 영역 지정으로 두고, 전체 화면은 명시적 플래그로 제공한다.

### 6.4 300dpi 재검토 — 실측 기반

페이지 실측 1105×1776px을 3.1의 A안(메타데이터만 300dpi)에 대입하면:

```
PDF 페이지 크기 = 1105/300 x 1776/300 inch = 94mm x 150mm
A4(210mm) 대비 폭 비율 = 0.45
```

94×150mm는 **문고본 크기**다. 밀도는 진짜 300dpi라 인쇄·확대 시 화질 손실이 없지만,
A4를 기대했다면 작게 느껴질 수 있다. 세 가지 선택지를 실측값으로 제시한다.

| 옵션 | 처리 | PDF 페이지 | 실효 밀도 | 파일 크기 |
|---|---|---|---|---|
| **A (기본)** | dpi 메타데이터 300 | 94 × 150 mm | 300 dpi | 기준 |
| B | dpi 메타데이터 150 | 187 × 301 mm | 150 dpi | 동일 |
| C | `--page-size a4` 배치 | 210 × 297 mm | ≈150 dpi | 동일 |

**세 옵션 모두 픽셀을 건드리지 않으므로 화질과 파일 크기가 동일하다.** 페이지 박스 표기만 다르다.
따라서 A를 기본으로 하고 B·C를 플래그로 제공한다. 업스케일(3.1의 B안)은 여전히 기각이다.

> **실제 화질을 높이는 유일한 방법**: 캡처 전에 **뷰어 창을 4K 모니터에서 최대한 크게** 키우는 것.
> 현재 페이지는 1776px 높이인데, 4K 모니터(2160px)에서 세로로 꽉 채우면 약 2100px까지 올라간다.
> 픽셀이 실제로 늘어나는 건 이 방법뿐이다. README에 안내한다.

### 6.5 클릭 전달·간격·완주 검증

#### 1. `CGEventPost` 클릭 전달 — **검증 완료**

이전 절까지는 미검증이었다. Task 11에서 실제로 확인했다: 빈 데스크톱 위 지점에
`clicker.click(30, 1220)`을 포스팅하고, 이와 독립적인 pynput 마우스 리스너로 관찰한 결과
`Button.left`의 press와 release가 정확히 `(30, 1220)`에서 관측되었다. 클릭 전후 화면 평균
차이는 2.686으로(빈 데스크톱이라 아무것도 바뀌지 않음), 커서 위치는 원래대로 복원되었다.

**결론: `CGEventPost`는 실제 시스템 이벤트 스트림에 정확한 전역 좌표로 클릭을 전달한다 —
검증 완료.**

클릭이 화면에 아무 영향도 주지 않는 상황(빈 데스크톱)에서도 파이프라인 자체는 정상
동작함을 별도로 확인했다: 클릭을 전혀 보내지 않고 4쪽을 캡처한 클릭-없음 종단 실행에서
화면이 전혀 바뀌지 않았으므로 3회 연속 정지가 정확히 설계대로 발동해 `STILL`로 종료되었다
(4쪽 캡처, 클릭 3회 = 쪽수−1, 소요 2.3초). 저장된 JPEG는 900×1200px, dpi (300, 300);
생성된 PDF는 4쪽, 0.47MB, 페이지 박스 76×102mm, 내장 이미지 900×1200px에 필터
`/DCTDecode`(무손실)였다. **OCR 판독 실패에 대비한 안전망(3.2의 2번 조건)이 설계대로
작동함을 실측으로 확인했다.**

#### 2. 클릭 후 페이지 렌더링 지연 시간 — **미측정, 실사용 확인 필요**

실제 뷰어를 대상으로 클릭을 보내며 전체 파이프라인을 아직 돌려보지 않아, 권장
`--interval` 값은 **아직 측정되지 않았다.** README에는 "2초부터 시작해 아래 스크립트로
중복 여부를 확인한다"는 절차만 방법으로 제시했다 — 이는 측정된 권장값이 아니라 출발점이다.
실제 뷰어로 클릭을 포함한 실행을 해봐야 확정할 수 있다.

참고로 실제 대상 뷰어의 진행률 표시 위치·형식은 확인되었다: 4K 모니터를 거의 채운 뷰어
화면(3836×2160)에서 진행률 줄은 y 2015–2026, 글자 높이 12px이며 `6%`가 x 387–406에
나타나고 같은 줄 x 418부터 절 제목이 이어진다(`6%  2절. 기능만 적은 문서가 왜 협업을
어렵게 만드는가`). `read_percent`를 이 실제 스크린샷에 대해 네 가지 서로 다른 폭의 영역
(타이트하게 `6%`만, 넉넉하게, 제목 포함, 매우 넓게)으로 각각 실행한 결과 **네 번 모두
정확히 6.0을 반환했다.** `%` 기호가 앵커 역할을 하므로 영역을 넉넉하게 잡아도 안전하며,
오히려 `%` 없이는 `2절`의 `2`를 진행률로 오독할 위험이 있었다는 뜻이다.

같은 화면에서 두 칼럼짜리 본문 스프레드(한 화면에 본문 두 단이 나란히 표시되고 클릭
한 번으로 두 칼럼이 함께 다음 장으로 넘어가는 레이아웃)도 확인했다 — 이 경우 한 번의
캡처 이미지가 두 칼럼을 통째로 담으므로 캡처 로직 변경은 필요 없다.

다음/이전 페이지 화살표는 페이지 영역 바깥 여백에 세로 중앙 정렬로 위치한다: 오른쪽
화살표 중심 (3556, 1079), 왼쪽 화살표 중심 (274, 1079).

#### 3. 진행률이 실제로 100%에 도달하는지 — **미측정, 실사용 확인 필요**

책 한 권을 클릭을 포함해 끝까지 완주하는 실행은 아직 수행되지 않았다. 따라서 뷰어의
진행률 표시가 실제로 100%까지 올라가 `COMPLETE`로 끝나는지, 아니면 99% 등에 머물러
`STILL` 폴백으로 끝나는지는 **아직 알 수 없다.** 다만 3.2의 설계상 어느 쪽이든
안전하다: OCR이 100%를 읽으면 정상 종료하고, 99%에서 멈춰 화면이 더는 바뀌지 않으면
3회 연속 정지 폴백이 대신 종료시킨다. 전체 소요 시간과 최종 PDF 용량도 책 한 권
분량으로는 아직 측정되지 않았다.


## 7. 로딩 대기 (2026-09-16 추가)

페이지를 넘긴 뒤 로딩 표시가 뜨는 동안 캡처하면 로딩 화면이 저장된다.
로딩 표시 영역을 지정해 두고, 로딩이 끝날 때까지 기다린 뒤 찍는다.

### 7.1 검출 지표 — 평균 차이는 쓸 수 없다

실제 로딩 표시는 회색 링 위에서 청록색 호가 도는 모양이고, 영역의 대부분은 흰 배경이다.
영역 전체의 평균 차이로 재면 배경이 차이를 희석해 회전을 놓친다. 실측값이다.

| 비교 | 평균 차이 | 변한 픽셀 비율 |
|---|---|---|
| 15도 회전 | 1.00 | 1.26% |
| 30도 회전 | 1.95 | 2.47% |
| 90도 회전 | 5.20 | 6.58% |
| 정지(동일) | 0.00 | 0.00% |

애니메이션 감지의 기존 임계값이 평균 차이 2.0이었으므로 **15도·30도 회전이 정지로
판정된다.** 그래서 **변한 픽셀의 비율**(밝기 차 24 초과)로 바꾸고 임계값을 0.3%로 두었다.
정지 0.00%와 뚜렷이 갈린다.

### 7.2 등록 그림 대조 — 전체 평균은 빈 화면을 오인한다

등록한 로딩 그림과 현재 화면을 전체 평균으로 대조하면, 로딩 표시가 대부분 흰 배경이라
**아무것도 없는 흰 화면까지 로딩으로 인식한다.** 실측으로 확인했다. 그대로 두면 여백이
흰 영역을 지정했을 때 매 페이지마다 타임아웃(30초)만큼 헛기다린다.

그림이 그려진 픽셀(배경보다 밝기가 24 넘게 어두운 자리)만 골라 그 자리끼리 비교하도록
바꾸어 해결했다. 검증 결과: 등록한 각도 4개 모두 인식, 흰 화면·본문 텍스트·검은 화면
모두 오탐 없음.

### 7.3 두 방식을 함께 쓰는 이유

등록 그림 대조만으로는 **등록해 두지 않은 회전 각도**를 놓친다(4장 등록 시 45·135·315도
미검출). 변화 감지만으로는 **멈춰 있는 로딩 표시**를 놓친다. 둘 중 하나라도 걸리면
대기하도록 해서 서로를 보완한다. 회전 12프레임 시뮬레이션에서 두 방식 모두, 그리고
등록 없이 변화 감지만으로도 끝까지 대기함을 확인했다.

### 7.4 5절 위험 표 정정 — pynput SIGABRT 는 상류 한계가 아니었다

5절과 이전 판단에서 "한 프로세스에서 pynput 키보드 리스너를 여러 번 만들면 SIGABRT"를
**상류 한계로 보고 파킹했으나 오판이었다.** 크래시 덤프에 두 스레드가 동시에
`keycode_context` 안에 있었다 — `AbortWatcher.__exit__` 가 `listener.stop()` 만 하고
스레드가 끝나기를 기다리지 않아, 다음 리스너가 시작될 때 겹친 것이다.

`__exit__` 에 `join(timeout=2.0)` 을 추가해 해결했다. 측정:

| | 수정 전 | 수정 후 |
|---|---|---|
| 순차 실행 | 16회 중 0건 (그러나 이후 3회 중 1건 발생) | **8회 중 0건** |
| 동시 실행 | 9회 중 1건 | **12회 중 0건** |

테스트 스위트를 동시에 돌리지 말라는 제약은 더 이상 필요하지 않다.
